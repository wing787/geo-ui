# ADR 0001: コンポーネントはソースのまま配布する

- 状態: 採用
- 決定日: 2026-11-15
- 見直しの目安: 下の「見直すタイミング」のどれかに当たったとき

## 背景

このリポジトリは、ポートフォリオと地理空間アプリが共有するデザインシステムである。
下流のアプリは git 依存でタグを指定して取り込む（例: `github:wing787/geo-ui#v0.1.0`）。npm には公開しない。

決定時点で配布しているのは `tokens.css` と `base.css` だけで、ビルドは要らない。
React コンポーネント（shadcn/ui ベース）はまだ無く、これをどう下流に届けるかを決める必要があった。

きっかけは2つある。

1. 当初の `package.json` は `exports["."]` が `dist/index.js` を指していたが、`dist/` は .gitignore 対象で
   ビルドスクリプトも無かった。git 依存で入れた下流には `dist/` が届かず、import が失敗する状態だった。
2. git 依存は、インストール時に依存側の `prepare` などのスクリプトを実行する。
   「下流の `npm install` でこのリポジトリのコードが走る」ことを許すかどうかが、セキュリティ上の論点になった。

## 前提と制約

- 開発者は1人。下流のアプリもすべて自分のもので、バンドラの設定を自分で変えられる。
- 「ここを直せば全アプリに効く」ことがこのリポジトリの目的である。
  特に凡例・タイムスライダーなどの地図UI部品は、全アプリで同じ作法に保ちたい（DESIGN-SYSTEM.md §7, §8）。
- npm には公開しない。
- 動く最小版から始め、必要になってから仕組みを足す。

## 検討した選択肢

| 方式 | 下流の install でコード実行 | 更新の伝わり方 | このリポジトリの手間 | 下流の手間 |
|---|---|---|---|---|
| A. `prepare` でビルド | あり | タグを上げれば伝わる | ビルド設定 | ほぼなし。ただし install が遅い |
| B. `dist/` をコミット | なし | タグを上げれば伝わる | ビルド設定＋毎回ビルドしてコミット | なし |
| C. shadcn registry（ソースをコピー） | なし | 伝わらない。各アプリで再取得 | registry の定義 | コンポーネントごとに `shadcn add` |
| D. ソース（TSX）のまま配る | なし | タグを上げれば伝わる | ほぼなし | バンドラにこのパッケージの変換を任せる設定 |
| E. CI でビルドし、GitHub Release に tarball を添付 | なし | URL のバージョンを上げれば伝わる | ビルド設定＋GitHub Actions | なし |

### A. `prepare` でビルド

git 依存のインストール時に下流のマシンでビルドする。

- 下流の install のたびにこのリポジトリのスクリプトが実行される。5案の中でセキュリティ上もっとも弱い。
- npm はビルドのために devDependencies まで入れるので、install が遅くなる。
- pnpm は最近のバージョンで依存のスクリプトを既定で実行しないはずで、許可設定が要る可能性がある（未確認）。

### B. `dist/` をコミット

ビルド結果をリポジトリに入れる。

- 下流から見れば確実に動く。
- 生成物が履歴に入り、diff が読みにくくなる。
- ビルドし忘れると、ソースと `dist/` が食い違ったままタグが打たれる。

### C. shadcn registry

自前の registry を定義し、下流が `shadcn add` でソースを自分のリポジトリにコピーする。

- ビルドも install 時スクリプトも要らず、下流の Tailwind がクラスを確実に検出できる。
- コピーされたコードには更新が伝わらない。アプリごとに少しずつ違う凡例ができていく。
- このリポジトリの目的と逆向きである。

### D. ソースのまま配る

`exports` を `src/index.ts` に向け、TSX のまま配る。変換は下流のバンドラが行う。

- ビルド設定が要らず、install 時スクリプトも要らない。
- タグを上げれば全アプリに変更が届く。
- 下流に設定が要る。Vite はそのまま動くことが多い。Next.js は `transpilePackages` に追加する。
  Tailwind v4 は、下流の CSS に `@source` でこのパッケージを走査対象として足す。
- 下流の TypeScript 設定と React のバージョンに引きずられる。

### E. CI でビルドして tarball を配る

タグを打つと GitHub Actions がビルドし、`npm pack` した tarball を Release に添付する。下流はその URL を依存に書く。

- 下流から見れば普通のビルド済みパッケージで、下流の設定に依存しない。もっとも堅牢。
- CI とリリース手順を作って維持する必要がある。

## 決定

**D（ソースのまま配る）を採用する。** あわせて、`package.json` に `prepare` / `postinstall` などの
インストール時スクリプトを追加しないことをルールにする。

## 理由

- 下流がすべて自分のアプリなので、D の弱点（下流の設定に依存する）が効きにくい。
- ビルド設定がゼロで済み、最小版から始める方針に合う。
- インストール時スクリプトが要らないので、下流の install でコードを実行させないというルールと両立する。
- 更新がタグで全アプリに届くので、C と違ってこのリポジトリの目的を損なわない。
- 後で E に移るとき、コンポーネントのコードを書き直す必要がない（下の「E への移り方」）。

A は install 時のコード実行、B は生成物の管理、C は目的との不一致を理由に退けた。
E は今の規模には手間が見合わないので見送った。D で困ったときの移行先とする。

## この決定で生じること

- `src/` の公開物は、下流のバンドラがそのまま処理できる書き方に保つ必要がある。
  このリポジトリだけで有効なパスエイリアスや、特殊なビルドプラグインに依存する書き方は使えない。
- 下流のアプリごとに初期設定（`transpilePackages`、`@source` など）が要る。手順は README に書く。
- 型チェックは下流の tsconfig でも走る。下流のほうが厳しい設定だと、下流側でエラーになりうる。
- React は peerDependencies に戻し、対応バージョンを明示する必要がある。

## 見直すタイミング

次のどれかが起きたら、この ADR を読み返して E への移行を検討する。

- 下流に、設定を合わせにくいアプリが増えた（別のバンドラ、別の TypeScript 設定、別の React メジャーバージョン）。
- 下流の初期設定でつまずくことが2回以上あった。
- 自分以外の人がこのパッケージを使うようになった。
- 下流のビルド時間が、このパッケージの変換のせいで目に見えて伸びた。
- アプリごとに部品を改造したい要求が増えた（この場合は E ではなく C を、対象の部品に限って検討する）。

## E への移り方

1. このリポジトリにビルド（tsup か Vite のライブラリモード）を足し、`dist/` に ESM と型定義を出す。
2. `exports["."]` を `src/index.ts` から `dist/index.js` に向け直す。
3. タグの push で動く GitHub Actions を足す。ビルドして `npm pack` し、tarball を Release に添付する。
4. 下流は依存を git 参照から tarball の URL に書き換え、`transpilePackages` などの設定を外す。

インストール時スクリプトを追加しないルールは、E でもそのまま守れる。

## 決定時点で未確認のこと

- D はまだ実装していない。最初のコンポーネントを作るときに、実際の下流（Vite / Next.js）で動作を確かめる。
- Tailwind v4 の `@source` で node_modules 内のパッケージを走査する書き方は、公式ドキュメントで確認する。
- pnpm が git 依存のスクリプトをどう扱うかは確認していない（A を選ばなかったので影響はない）。
- 下流がどのパッケージマネージャを使うかは決まっていない。

## 関連

- タグでの配布と main の保護は、同じ日に決めて実施済み（README、CLAUDE.md「変更の作法」）。
- npm に無関係なパッケージ `geo-ui` があるため、パッケージ名はスコープ付きの `@wing787/geo-ui` にしている。
